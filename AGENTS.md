# AGENTS.md — house-palette

Spec sheet for the palette source of truth. Read this before editing anything in
this tree.

## What this repository owns

`palette.json` owns every colour and alpha the machine's surfaces read. The
renderer owns the files listed in `src/targets.ts`; those files carry a generated
header and are overwritten on every render. Everything else — geometry, motion,
glyphs, app layout, and every live application config — belongs to the tree that
consumes it.

Consumers commit the generated files in their own repositories. Nothing in a
consumer build reaches back here at runtime; drift is visible in that consumer's
own `git status` and caught by `bin/render --check`.

## Commands

```sh
bin/render                                  # write every target
bin/render --check                          # fail (exit 1) on stale, hand-edited or missing output
bin/render --target <name> [--target <name>]
bin/render --out <dir> [--tinshell <dir>]    # fixture roots; never a real tree
bin/render --list                            # targets, held-back entries, apply steps

node --test tests/*.test.ts                 # the whole suite, no dependencies

HOUSE_PALETTE_REVISION=fixture bin/render --out tests/golden --tinshell tests/golden/tinshell
```

Node 22 runs the TypeScript sources directly by stripping types: no build step,
no `node_modules`, no lockfile. Keep it that way — an import must carry its
`.ts` extension, and no syntax that needs transformation (enums, namespaces,
parameter properties) may appear in `src/`.

## Adding or changing a role

1. Add the role to `palette.json`. A role is a lower-case hex string, or an
   object carrying `alpha`, the `frozen` flag, a one-line `note`, a `derive`
   formula, or an `alias`.
2. Add the same role to `palette.schema.json` — a test asserts the two sets are
   equal in both directions, so one without the other fails.
3. If the value is derived, write the formula in `derive` and make the test in
   `tests/derivations.test.ts` recompute it. Do not leave a derived number with
   no formula: that is how a hand-tuned value hides among the derived ones.
4. Regenerate the goldens and review the diff of the generated bytes.
5. Name the role for the job it does, never for its colour.

Rules that decide the shape of a value:

- **Alpha decides the syntax.** A syntax that cannot carry alpha receives the
  role's solid composite from `palette.json:composites`, never a value picked by
  eye. `composites` is asserted to be the role painted over `panel-base`.
- **A frozen value is carried, never derived from, averaged or normalised.** The
  per-surface panel alphas exist precisely because one alpha does not read the
  same through two surfaces. Changing a frozen value is a deliberate edit that
  changes a test.
- **One decision, one spelling.** If two roles must hold the same value, one is
  an `alias` of the other, so they cannot drift apart.

## Generated output

- Every generated file starts with a header naming the source, its digest and
  the regenerating command. JSON destinations cannot carry a comment, so they
  record provenance in the manifest instead.
- A template addresses tokens by role name: `{{accent}}`, `{{hairline.css}}`,
  `{{hairline.solid}}`, `{{glass.dock-menu.css}}`, `{{ansi.4}}`, `{{pi.accent}}`.
  An unknown token throws, so a stale template cannot render a blank colour.
- Everything is deterministic apart from the recorded source revision, which a
  fixture render pins through `HOUSE_PALETTE_REVISION`.

## Drift checks

`bin/render --check` catches a stale generated file and a hand edit inside one.
A palette value re-spelled in a consumer file is caught by a literal scan over
that tree, using the role set here as the list of forbidden literals. The
generated files are the only place a value may appear; the consumers' own
hand-written carriers shrink to importing them.

## Wiring, and what is deliberately not automatic

The renderer never edits a live config. Each destination whose loader needs a
line added once — kitty's `include`, git's `include.path`, tmux's `source-file`,
the GTK CSS `@import`s, the GTK2 `include`, the shell `require` — has that step
recorded in `src/targets.ts` and printed by `bin/render --list`.

Two destinations need more than a line:

- **KDE and Qt INI files** have no include, so `kdeglobals.colours.ini` is staged
  for a merge step. The Qt palette fragment is not generated at all: its keys are
  positional colour lists whose slot meaning is not stated, and filling that shape
  would be guessing.
- **VS Code's injected CSS** is baked into a root-owned install by the extension,
  so a changed import needs the existing re-apply path to run. A reload is not
  enough and must not be reported as one.

Held-back destinations (hyprlock's config, Firefox profile CSS, the vibrancy CSS
that already holds hand-authored rules) are listed with their reasons in
`src/targets.ts`; each one waits for a confirmed load mechanism or a stated
policy, not for someone to guess one.

## Gotchas

- **A reload printing `ok` proves nothing for a compositor config field.** Verify
  a wired-in palette fragment with a fresh `hyprctl reload` **and** an empty
  `hyprctl configerrors`.
- **A capacity-limited syntax is not a smaller palette.** Dropping alpha for a
  consumer means taking that consumer's declared composite, not skipping the
  value.
- **The goldens are the review surface.** A rendered diff is the change to read;
  never regenerate goldens to make a failing test pass without reading it.
- **Never render into a real tree from a test or a probe.** `--out` and
  `--tinshell` exist for that; the machine's own files are written by an
  explicit render against the real tree.
